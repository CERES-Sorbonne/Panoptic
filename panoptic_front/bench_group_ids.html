Group ID Resolution Benchmark

Compares 6 strategies for resolving a leaf-group ID from a 3-level value path [numeric, string, tagId] with property IDs [1, 2, 3]. Each test generates N unique paths and measures the cold phase (first-pass ID creation — populates any internal state) and the hot phase (second-pass lookup of the same paths).

# Approach Cold (ms) ns/op Hot (ms) ns/op Unique IDs Notes

Approaches

A. GroupValueIndex (nested Map) — current production code. One Map per groupBy level; descend through the tree by value; null-key entry at each leaf holds the sequential ID.
B. Flat Map<string, number> — concatenate values into one canonical string, store in a single Map keyed by that string. Sequential IDs.
C. FNV-1a 53-bit hash (type-dispatched) — stateless. For each value, branch on typeof: number → mix as int; string → char-by-char FNV-1a. PropIds mixed in so groupBy reorder doesn't alias.
D. FNV-1a 53-bit hash + on-the-fly string interning — same hash, but strings are first interned through a Map<string, int>. Inner loop becomes pure numeric arithmetic. Cold cost includes building the intern table.
E. Canonical string ID — concatenated string itself is the ID. No hashing, no Map. Useful as a baseline for "what does just-make-a-string cost?"
F. JSON.stringify ID — common lazy approach. Compares against the slowest realistic option.
G. FNV+Murmur3 hash (true 53-bit) — same shape as C, but h2 uses a Murmur3-style mixer (rotate + two different primes) instead of a second FNV. This makes the two streams algebraically independent — fixes the entropy ceiling that made C/D effectively 32-bit.
H. FNV+Murmur3 + string intern — same idea as D, with the corrected hash. Expected to be the fastest hot pass with near-zero collisions.

Data shape

  • Each path: [i % 1000, "label_" + Math.floor(i / 100), i % 100].
  • By construction all paths are unique for any N up to 3M (the triple of those three expressions identifies i uniquely).
  • Average string length: ~10 chars; ~30k distinct strings across 3M paths.
  • Each approach runs once after warm-up; per-op times have very low variance at N = 3M.

Reading the table

  • Cold includes any state population (Map fill, intern table build).
  • Hot reruns lookups on the same paths with state already populated.
  • ns/op = total time / N. Easier to compare across N values.
  • For stateless approaches (C, E, F), cold ≈ hot — they're pure functions.
  • For stateful approaches (A, B, D), hot < cold (no allocations on the second pass).
  • Best result in each column is highlighted green.
